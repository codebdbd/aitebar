# Инструкция для ИИ-агента по выполнению миграции AiteBar на .NET 10

## Задача

Полностью выполнить план из файла `MIGRATION_NET10.md`.

Цель — перевести AiteBar с .NET 8 на .NET 10 без изменения существующего функционала, интерфейса и архитектуры.

## Правила

1. Сначала полностью изучить `MIGRATION_NET10.md` и фактическую структуру репозитория.
2. Выполнять этапы плана последовательно.
3. Не ограничиваться заменой версии SDK и TFM.
4. Не делать рефакторинг, переименование, форматирование, изменение UI или архитектуры.
5. Не обновлять NuGet-пакеты без подтверждённой несовместимости.
6. Не отключать тесты, warnings и анализаторы ради успешной сборки.
7. Не использовать временные обходы и костыли.
8. Не удалять исходники, пользовательские файлы и несвязанные изменения.
9. Не утверждать, что проверка выполнена, если она не выполнялась фактически.
10. Любое изменение должно быть напрямую связано с миграцией на .NET 10.

## Порядок работы

### 1. Проверить исходное состояние

Проверить:

- `git status`;
- текущую ветку;
- установленные SDK;
- `global.json`;
- `Directory.Build.props`;
- оба `.csproj`;
- lock-файлы;
- NuGet-конфигурацию;
- скрипт инсталлятора;
- CI-файлы;
- все упоминания `.NET 8`, `8.0.421` и `net8.0-windows`.

До изменений выполнить, если окружение позволяет:

```powershell
dotnet restore AiteBar.sln
dotnet build AiteBar.sln -c Release
dotnet test AiteBar.Tests\AiteBar.Tests.csproj -c Release
```

Зафиксировать существующие ошибки, warnings и результаты тестов.

### 2. Подготовить ветку и очистить артефакты

Создать ветку `migration/net10`, если её ещё нет.

Удалять только указанные в плане каталоги `bin`, `obj`, старые publish-артефакты и lock-файлы.

Перед удалением проверить, что каждый путь находится внутри репозитория.

### 3. Обновить конфигурацию

Изменить:

- `global.json`;
- `AiteBar/AiteBar.csproj`;
- `AiteBar.Tests/AiteBar.Tests.csproj`.

Использовать реально установленную версию .NET 10 SDK.

Заменить:

```text
net8.0-windows
```

на:

```text
net10.0-windows
```

Не добавлять `LangVersion`, если это не требуется для устранения конкретной проблемы.

### 4. Перегенерировать lock-файлы

Удалить только:

```text
AiteBar/packages.lock.json
AiteBar.Tests/packages.lock.json
```

Затем выполнить:

```powershell
dotnet restore AiteBar.sln --force-evaluate
```

Проверить:

- оба lock-файла созданы;
- используется новый TFM;
- restore завершён без ошибок;
- версии пакетов не изменились неожиданно.

### 5. Выполнить сборку

```powershell
dotnet build AiteBar.sln -c Release --no-restore
```

При ошибке:

1. определить первопричину;
2. внести минимальное исправление;
3. повторить сборку;
4. не подавлять диагностику без обоснования.

Требуемый результат: `0 errors`.

### 6. Проверить зависимости

Проверить совместимость пакетов, указанных в плане, особенно:

- Sentry;
- SkiaSharp;
- SkiaSharp.NativeAssets.Win32;
- Svg.Skia;
- Microsoft.NET.Test.Sdk;
- xUnit;
- coverlet.

Обновлять пакет только при доказанной необходимости.

После любого обновления повторить restore, build и tests.

### 7. Запустить тесты

```powershell
dotnet test AiteBar.Tests\AiteBar.Tests.csproj -c Release --no-build
```

Проверить:

- все ранее проходившие тесты проходят;
- количество тестов не уменьшилось;
- нет новых skipped-тестов;
- STA-тесты WPF работают;
- reflection-based тесты работают.

Не изменять тесты только ради успешного результата.

### 8. Проверить P/Invoke и marshalling

Проверить все файлы и вызовы, указанные в плане.

Особое внимание:

- `StructLayout`;
- `FieldOffset`;
- размеры Win32-структур;
- x64 layout;
- `INPUTUNION`;
- lifetime delegate для mouse hook;
- регистрацию и освобождение hotkey;
- установку и снятие hook;
- освобождение unmanaged memory.

Не выполнять миграцию `DllImport` → `LibraryImport` в рамках этой задачи.

### 9. Проверить приложение

Запустить Release-сборку и проверить доступные сценарии из плана:

- запуск и завершение;
- панель на всех четырёх сторонах;
- контексты;
- tray;
- hotkeys;
- mouse hook;
- single-instance;
- Quick Note;
- иконки;
- SkiaSharp;
- System.Drawing;
- Screen API;
- FolderBrowserDialog.

Для каждой проверки использовать статус:

- `PASS`;
- `FAIL`;
- `BLOCKED`;
- `N/A`.

Не ставить `PASS` только на основании чтения кода.

### 10. Собрать инсталлятор

```powershell
.\installer\Build-Installer.ps1
```

Проверить:

- publish проходит;
- используется `net10.0-windows`;
- создан итоговый артефакт;
- native-зависимости присутствуют;
- старые `net8.0-windows` артефакты не попали в сборку;
- установленное приложение запускается, если установка безопасно доступна для проверки.

### 11. Обновить документацию

Обновить актуальные сведения минимум в:

- `AGENTS.md`;
- `docs/architecture.md`;
- `docs/technical-reference.md`;
- `CHANGELOG.md`.

Также проверить README, CI и скрипты.

Не изменять исторические записи о старых версиях.

### 12. Финальная проверка

Выполнить:

```powershell
dotnet restore AiteBar.sln --force-evaluate
dotnet build AiteBar.sln -c Release --no-restore
dotnet test AiteBar.Tests\AiteBar.Tests.csproj -c Release --no-build
.\installer\Build-Installer.ps1
git diff --check
git status --short
git diff --stat
```

Повторно найти все активные упоминания:

- `.NET 8`;
- `8.0.421`;
- `net8.0-windows`;
- старых output-путей.

Каждое оставшееся совпадение объяснить.

## Итоговый отчёт

В конце предоставить краткий отчёт:

1. Итоговый статус: `SUCCESS`, `PARTIALLY VERIFIED` или `FAILED`.
2. Список изменённых файлов.
3. Результат restore.
4. Результат сборки.
5. Результат тестов.
6. Изменения зависимостей.
7. Результат проверки P/Invoke.
8. Результат ручных проверок.
9. Результат сборки инсталлятора.
10. Оставшиеся проблемы и заблокированные проверки.
11. Полный список фактически выполненных команд.

Статус `SUCCESS` допустим только если обязательные автоматические проверки действительно прошли.

Если часть ручных проверок недоступна, использовать `PARTIALLY VERIFIED`.

Если restore, build, tests или installer завершаются ошибкой, использовать `FAILED`.
