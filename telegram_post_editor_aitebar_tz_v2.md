# Telegram Post Editor — техническое задание на встроенную утилиту AiteBar

**Версия ТЗ:** 2.0  
**Дата:** 15 ноября 2026 года  
**Статус:** согласованная архитектурная основа для реализации, **приложение ещё не разработано**  
**Продукт:** существующее Windows-приложение **AiteBar**  
**Модуль:** `TelegramPostEditor` — встроенная утилита, а не отдельное приложение  
**Приоритет источников:** актуальные исходники AiteBar → действующие контракты/тесты → документация репозитория → настоящее ТЗ. При расхождении текущего репозитория со снимком на Google Drive требуется уточнять реализацию, **не переписывая уже работающие системы**.

## 0. Зафиксированные решения и запреты на расширение объёма

1. **Не создавать отдельный десктопный продукт.** Telegram Post Editor — обычная встроенная утилита AiteBar, запускаемая с панели/горячей клавишей по существующим паттернам.
2. **Дизайн не разрабатывается заново.** Использовать общие окна, темы, ресурсы, иконки, локализацию, отступы, состояния контролов и UX-паттерны AiteBar. **Отменены** самостоятельный SaaS-дизайн, отдельная палитра, новый дизайн-кит, Figma-этап, Tailwind/shadcn, React UI и отдельная дизайн-система. Термин «современный SaaS» из ТЗ v1.0 не действует.
3. **Каталог ИИ-провайдеров не расширять.** Провайдеры, адреса, API-ключи и их переключение **уже настроены в актуальном AiteBar, по информации владельца проекта**. Не создавать второй каталог, отдельную форму подключения, второй механизм ротации, хранилище ИИ-ключей или новую настройку Groq/OpenRouter и других сервисов. Отклонённый раздел v1.0 с 55 сервисами **исключён**. Использовать существующий `AiGateway` и его действующие настройки; при несовместимости оформить конкретный блокер, а не менять общий механизм без решения владельца.
4. **Функциональность редактора сохраняется:** создание/оформление постов, предпросмотр, ИИ-обработка с выбираемыми инструкциями, публикация в несколько каналов, очередь, календарь, серверное выполнение при выключенном ПК, история, медиа, тестовые публикации, повторное использование, безопасность и резервные копии.
5. Никакие существующие утилиты, исходные стили, сохранённые ИИ-подключения, пользовательские настройки и данные AiteBar не должны нарушаться.
6. Актуальная версия AiteBar может быть новее копии на Google Drive. Перед написанием кода исполнитель **сначала** сверяет перечисленные пути и действующие контракты в рабочем репозитории; добавления делаются минимальными и по принятым соглашениям.

## 1. Цель и конечный результат

Реализовать внутри AiteBar полнофункциональную утилиту для Telegram-каналов: **создание → локальный черновик → ИИ-редактирование → Telegram-превью → проверка → выбор одного/нескольких каналов → немедленная публикация или серверная очередь → журнал результатов → редактирование/повторное использование**.

Критический сценарий: пользователь подготовил 10 постов, назначил публикации на неделю для двух или более каналов, закрыл AiteBar и выключил Windows; сервер продолжил отправку без участия компьютера. Другой критический сценарий: приложение работает без сервера в режиме черновиков, ИИ-обработки, предпросмотра и ручной отправки «сейчас» (при наличии интернета).

Первая версия рассчитана на **одного владельца** и несколько каналов; роли редактора, команды, платёжные тарифы и CRM **не входят** в v1.0. Работа через официальный **Telegram Bot API**, а не через персональный Telegram-аккаунт; права бота должны проверяться.

### 1.1. Главные сценарии пользователя

- Создать новую публикацию вручную или из шаблона, форматировать и добавить медиа.
- Выбрать уже доступную модель из текущих настроек AiteBar, выбрать сохранённую инструкцию и получить вариант поста, не потеряв оригинал.
- Подготовить разные редакции одной публикации для разных каналов.
- Предварительно посмотреть результат и отправить в тестовый канал.
- Опубликовать сейчас либо поставить каждый вариант в очередь со своим временем.
- Отследить статус **по каждому каналу отдельно**, включая ошибки и неоднозначные результаты.
- Исправить уже опубликованный пост там, где тип сообщения и права Telegram позволяют редактирование; повторно использовать запись.
- Перезапустить приложение или восстановить сервер, не потеряв черновики и очередь.

### 1.2. Не входит в проект

Полноценный Telegram-клиент, чтение личной переписки, автоматическая регистрация Telegram-аккаунтов, автоматическая регистрация ИИ-сервисов/получение ключей, новые ИИ-провайдеры и их UI, самостоятельный установщик редактора, новая дизайн-система, парсинг закрытых каналов, коммерческие подписки, автоматические публикации без предварительного утверждения пользователем, аналитика не предусмотренная доступными API.

## 2. Технологический стек и границы компонентов

| Уровень | Технология | Решение |
|---|---|---|
| Основное приложение | **AiteBar: .NET 10 / C# / WPF (`net10.0-windows`)** | Сохранить |
| Интерфейс | XAML + WPF, `DarkWindow`, классы окон AiteBar | Сохранить общий стиль |
| Запуск/регистрация | `[Utility]`, `UtilityBase<TWindow>`, `UtilityRegistry`, `UtilityButtonCatalog` | Использовать существующий контракт |
| ИИ | **существующий `AiGateway`** и текущее конфигурирование моделей/подключений | Переиспользовать без расширения |
| ИИ-ключи | Текущее хранилище AiteBar (`WindowsAiCredentialStore` или актуальный эквивалент) | Не дублировать |
| Локальные данные утилиты | **SQLite + Microsoft.Data.Sqlite**, WAL, транзакции, миграции | Новое изолированное хранилище |
| Текстовый редактор | WPF `RichTextBox`/`FlowDocument` + собственная сериализация Telegram-документа | Новая утилита, переиспользование подходов Quick Note |
| Telegram | HTTPS + Bot API, `HttpClient` с DI и обработкой ошибок | Новый адаптер |
| Сервер планирования | **ASP.NET Core 10 Minimal API + .NET `BackgroundService`** в одном небольшом Linux-процессе | Только для серверной очереди |
| Серверная БД | **SQLite (WAL)** в v1.0, один экземпляр сервера | Минимальная инфраструктура |
| Серверное медиа | Локальное файловое хранилище на VPS, контроль хешей | Не зависеть от ПК в момент отправки |
| Транспорт ПК ↔ сервер | HTTPS REST + токен авторизации, версии протокола | Только планирование/статусы/медиа |
| Развёртывание | systemd + HTTPS reverse proxy; Docker Compose **допустим, но не обязателен** | Без Redis/PostgreSQL/Node.js |
| Тесты | существующий xUnit-проект `AiteBar.Tests` + серверные .NET-тесты | CI в существующем репозитории |
| Поставка | действующий build/publish и установщик AiteBar | Никакого второго установщика |

**Не применять Tauri, Rust, React, TypeScript, Node.js, Fastify, Drizzle, pg-boss и отдельный фронтенд.** Эти предложения из ТЗ 1.0 отменены.

### 2.1. Режимы работы

1. **Локальный:** редактор, локальные черновики, библиотека, ИИ, предпросмотр, экспорт, публикация «сейчас» через прямой Telegram Bot API.
2. **С сервером:** всё перечисленное плюс загрузка утверждённого снапшота поста и медиа на сервер, надёжная очередь, публикация после отключения ПК, синхронизация статусов.
3. **Офлайн:** работа с существующими черновиками, изображениями, инструкциями и календарём, сохранение локальных изменений; ИИ и отправка доступны лишь если соответствующие подключения достижимы. Запись в **серверную очередь** подтверждается исключительно после получения ответа сервера.

**Особое ограничение:** если сервер настроен, отправка «сейчас» может идти через сервер ради единого журнала; при недоступности сервера локальную отправку разрешать **только после явного выбора** пользователя и обозначения, что это отдельный путь доставки.

### 3.2. Точки подключения (проверить в рабочем репозитории)

1. Создать `[Utility] class TelegramPostEditorUtility : UtilityBase<TelegramPostEditorWindow>` с `Id = "TelegramPostEditor"`.
2. Зарегистрировать в общем `UtilityButtonCatalog` (тот же глиф/цветовой подход, что текстовые утилиты) и в стандартном механизме отображения и запуска кнопок AiteBar.
3. Добавить флаг видимости в `Models.cs` (`ShowPresetTelegramPostEditor`), копирование/сохранение через `AppSettingsService`, настройку видимости в стандартных настройках. Не добавлять собственную глобальную панель настроек.
4. Подключить запуск через существующие `ActionService`/`UtilityRegistry` и лишь необходимый dispatch в `MainWindow` (как для `TextProcessing`/`ZenEditor`). Горячую клавишу добавить по действующему контракту, если пользователь её включил.
5. Добавить локализацию в существующие `Resources/Strings*.resx`, описание в `docs/functions.md`, руководство и тесты.
6. Окно наследует `DarkWindow` и использует `WindowClass = Workspace` либо соответствующий действующий тип широкого окна в новой версии. Размещение, восстановление, фокус и DPI — стандарт AiteBar.
7. Получать доступ к **одному существующему общему** `AiGateway` через имеющуюся точку выдачи сервиса/DI; не создавать в утилите собственный каталог/сервис ключей. Если в текущем коде есть локальные экземпляры шлюза, выбрать общий принятый в AiteBar способ, не меняя его настройки.
8. Не изменять форматы данных Quick Note/Zen Editor и механизмы их редактирования; использовать только совместимые общие паттерны и готовые вспомогательные части.

### 3.3. Внешний вид и UX — только общие паттерны AiteBar

- Отдельное полноразмерное окно утилиты, **не** ещё одно мини-оверлей-окно. Три функциональные области допустимы: библиотека слева, редактор по центру, предпросмотр справа; если ширины недостаточно — переключаемая вкладка предпросмотра.
- Оформление всех областей, цвета, рамки, кнопки, контекстные меню, иконки, диалоги, строка статуса, настройки и поведение горячих клавиш — **из текущих ресурсов AiteBar**, без новых палитр и визуальных стандартов.
- Элементы управления могут отличаться по функциям, но не по стилю. Не менять приложение ради нового редактора.
- Все основные операции должны быть доступны с клавиатуры; вкладки и фокус — по паттернам проекта. Существующие уровни локализации (в том числе RU/UK/EN) сохраняются.

## 4. Редактор публикаций и библиотека

### 4.1. Модель документа

`PostDocument`: `Id`, `Title`, `Blocks`, `TelegramEntities`, `Media`, `Tags`, `FolderId`, `CreatedUtc`, `UpdatedUtc`, `Revision`, `WorkflowStatus`, `ChannelOverrides`, `InstructionVersionId`, `AiGenerationMetadata`, `LastValidation`.

**Единый источник истины — структурированный документ**, а не Markdown-строка. Хранить текст с диапазонами оформления/типами блоков и отдельными прикреплёнными медиа. Превью и отправляемое сообщение строить из этого же документа. Telegram-специфичная сериализация должна быть отдельным модулем.

### 4.2. Редактирование

- Создание, открытие, дублирование, переименование и удаление черновиков (с корзиной и восстановлением).
- WYSIWYG-форматирование поддерживаемых Telegram-форматов: жирный, курсив, подчёркивание, зачёркивание, спойлер, код/моноширинный, цитаты, гиперссылки; необходимые списки — как текстовые конструкции либо поддерживаемые блоки, в зависимости от актуального API.
- Вставка текста из браузера/Word/буфера с нормализацией небезопасной разметки. Переносы строк не должны автоматически превращаться в двойные пустые абзацы.
- Undo/Redo, копирование/вставка, поиск по документу, выделение и применение форматирования к выделенному фрагменту.
- Подсчёт длины текста и подписей; отображение ошибок согласно **актуальному методу Telegram Bot API**, а не одному фиксированному лимиту на все разновидности публикаций.
- Открываемые ссылки, вставка ссылок с отображаемым текстом, переключение предпросмотра веб-ссылки.
- Настраиваемые теги, папки, фильтры по дате, каналу, статусу и полнотекстовый поиск по постам.
- История редакций; возможность восстановить версию, не теряя последующие публикации и записи истории.
- Избранное для часто используемых черновиков; выбор между рабочим названием документа и фактическим заголовком публикуемого сообщения.
- При превышении допустимой длины предложить «Сократить через ИИ» либо «Разбить на последовательные сообщения»; выполнять разделение **только после явного подтверждения**, предварительно показывая все части и их последовательность.
- **Автосохранение** после паузы ввода (ориентир 500–1000 мс) и при уходе из редактора/закрытии. Атомарное сохранение, восстановление после аварийного завершения.
- Раздельные статусы: локально сохранено; отправлено на сервер; подтверждено сервером; опубликовано в Telegram.

### 4.3. Медиа

- Прикрепление: фото, видео, GIF/анимации и документов — только в пределах поддерживаемых Telegram Bot API форматов.
- Drag-and-drop, удаление, изменение порядка, название/подпись, превью и контроль форматов/размеров.
- Альбомы там, где API поддерживает нужное сочетание и количество файлов; заранее предупреждать о несовместимых комбинациях.
- Локальное файловое хранилище с уникальными именами, хешами SHA-256 и очисткой неиспользуемых файлов только после проверки ссылок из документов и заданий очереди.
- При планировании **загружать медиа на сервер до подтверждения задания**, чтобы выключенный ПК не блокировал публикацию.
- Для уже загруженных файлов использовать возвращённый Telegram `file_id`, когда его применение соответствует актуальным ограничениям Telegram.
- Медиа, относящееся к одной публикации в разных каналах, переиспользовать безопасно, сохраняя отдельные результаты отправки.

### 4.4. Шаблоны

Шаблон поста: название, содержимое, необязательные медиа-заполнители, тип задачи, инструкция по умолчанию. Поддержать: создание из текущего поста, применение к новому черновику без изменения исходного шаблона, импорт/экспорт в JSON; несколько встроенных примеров — новости, обзор, анонс, инструкция — без привязки к конкретному каналу.

## 5. ИИ в редакторе — существующие провайдеры AiteBar

### 5.1. Строгое ограничение

**В этом проекте НЕ разрабатывать и НЕ изменять:** подключение новых провайдеров, Base URL, страницы выдачи ключей, систему API-ключей, их приоритеты и ротацию, действующий каталог моделей, глобальную форму «Нейросети» и внутренний роутинг `AiGateway`. Использовать в точности реализованное в актуальной версии AiteBar. Расширение списка из `services.txt` не входит в задание.

### 5.2. Что реализовать внутри новой утилиты

- Выпадающий выбор **существующего** ИИ-подключения/модели (или режима «Автоматически») через публичный интерфейс `AiGateway`, без доступа к значениям API-ключей.
- Действия: создать пост по заданию, улучшить, сократить, исправить ошибки, переписать в выбранном стиле, предложить заголовки, перевести, адаптировать к каналу, оформить для Telegram, сделать альтернативные варианты.
- Результат генерации выводится **в отдельной области предложений**; исходный текст не перезаписывается до нажатия «Применить». Поддержать отклонение, копирование, сравнение/дифф, **«Применить выделенное»**, отмену и повторный запрос.
- Действие «Сравнить модели»: пользователь явно выбирает две или несколько **уже настроенных** моделей, подтверждает отдельные API-запросы, получает варианты рядом и выбирает текст либо фрагменты; не добавлять никаких провайдеров или ключей.
- Во время запроса отображать ход выполнения/потоковый вывод, кнопку «Остановить», фактически выбранную модель и конкретную ошибку в рамках данных `AiGateway`.
- Если существует несколько ключей и механизм переключения, утилита пользуется им **автоматически**, не реализуя собственную ротацию и не навязывая конкретный `PreferredConnectionId`, который исключает системный failover. Требование к пользователю — не вводить ключи повторно.
- Сохранять метаданные: время, режим обработки, ID провайдера, ID модели, ID инструкции и её версии, параметры запроса, если применимо. **Не сохранять секреты**.
- Отсутствие подключённых моделей не блокирует ручное создание/публикацию.
- **Не запускать ИИ для запланированного поста на сервере:** в очередь уходит только окончательно утверждённое содержимое.

### 5.3. Библиотека инструкций (НОВАЯ, но не каталог провайдеров)

- Создание, переименование, редактирование, дублирование, удаление, поиск и категории пользовательских инструкций.
- Текст инструкции редактируется **непосредственно в утилите**; переключение из верхней панели редактора без открытия общих настроек AiteBar.
- Инструкция по умолчанию для каждого канала и отдельная инструкция на конкретный пост; выбор модели/провайдера допускается как **ссылка на существующую конфигурацию**, а не повторная настройка API.
- Комбинация: правила достоверности и безопасности → стиль канала → инструкция вида публикации → конкретное задание пользователя. Отображать итоговую применённую последовательность и предупреждать о конфликтующих указаниях.
- Импорт/экспорт инструкций в Markdown и JSON, версии/история изменений, восстановление старой версии, тестовая генерация в отдельном черновике.
- Для воспроизводимости хранить **снимок версии инструкции, использованной при генерации**, даже после её дальнейшего редактирования.
- По умолчанию ИИ не должен добавлять непроверенные факты, фиктивные источники или произвольные ссылки. Пользователь утверждает результат сам.

## 6. Telegram-превью и проверка перед отправкой

- Превью обновляется при редактировании документа и переключении канала/варианта.
- Отображать название и аватар канала (если сведения доступны), оформленный текст, цитаты, спойлеры, ссылки, превью изображения, видео, альбома и кнопок.
- Предпросмотр показывает **примерное** отображение Telegram, а не гарантированный пиксель-в-пиксель результат на всех клиентах. Если реальный тип сообщения не поддержан имитацией — явно обозначить ограничение.
- Режимы «свёрнуто» / «полностью», когда это применимо к конкретному типу сообщений.
- Одновременный подсчёт лимитов Telegram и объяснение точного нарушенного ограничения; валидация перед каждым выходом в тестовый/основной канал.
- Проверять: наличие канала и прав, токен бота, валидные URL и кнопки, существование и совместимость вложений, подписи, ограничения метода, доступность медиа на сервере для запланированных задач.
- Предупреждать о внешних ссылках/карточках, которые Telegram генерирует самостоятельно и может отобразить неидентично локальному предпросмотру.
- Реализовать **«Тестовая публикация»** в назначенный тестовый канал с обязательным явным подтверждением. Тестовая отправка не считается публикацией в основные каналы.

## 7. Боты, каналы, мультипубликация

### 7.1. Подключение

- Добавить бота по токену, проверить `getMe` и отдельно административные права `getChatMember`/разрешения на публикации, где доступны.
- Добавить публичный канал по `@username` или приватный по надёжному `chat_id`. Учитывать ограничения получения сведений из приватных каналов.
- Сохранять для канала: `ChannelId`, название, Telegram `chat_id`, `username` (если есть), `BotId`, стиль/инструкция по умолчанию, тестовый флаг, часовой пояс, настройки предпросмотра/уведомлений.
- Для одного бота разрешить несколько каналов; для нескольких ботов — разные каналы.
- Бот должен быть администратором канала с правом публикации. При потере прав: отдельный статус, не бесконечные повторы.
- Telegram-токен хранить локально через **отдельный безопасный секрет типа Telegram**, а не в поле JSON или AI-хранилище под тем же префиксом. Не отображать после сохранения.

### 7.2. Массовая отправка без дублей

- Выбор нескольких каналов чекбоксами, массовое выделение/снятие, фильтрация.
- Один исходный пост + **вариант для каждого канала** (текст, медиа, кнопки, инструкция и расписание могут различаться).
- Для каждой пары `post_revision + channel` создавать **отдельную целевую публикацию** со своим ID, статусом, временем, попытками и ссылкой на Telegram-сообщение.
- При частичной ошибке повторять **только** неуспешные цели; успешно опубликованные не отправлять повторно автоматически.
- Для альбомов хранить группу Telegram message IDs, а не один ID.
- Кнопки URL под сообщениями (inline keyboard) и настройки уведомления/превью ссылок — по возможностям конкретного метода API.
- Обновление текста/медиа уже опубликованной записи разрешать лишь там, где это допускает Telegram. Удаление — с подтверждением, отдельным результатом по каждому каналу.
- История содержит Telegram `chat_id`, `message_id`/группу IDs, фактическое время, тип отправки, результат, последнюю ошибку, ссылку, если её можно корректно построить.

### 7.3. Импорт и повторное использование

- Создать новый черновик из опубликованного/ранее подготовленного поста без изменения оригинала.
- Импортировать текст из буфера и URL статьи по **явному запросу пользователя**; автоматическая выжимка возможна только при технически корректном извлечении текста, с сохранением ссылки на источник.
- Импорт из пересланного Telegram-сообщения — только если бот действительно получает такое сообщение через разрешённый API; без обещания универсального доступа к любому каналу.

## 8. Планировщик и календарь

### 8.1. Состояния

`DRAFT → READY → QUEUED_LOCAL → QUEUED_SERVER → SENDING → SENT`; дополнительные состояния: `PAUSED`, `RETRY_WAIT`, `FAILED`, `UNKNOWN_RESULT`, `CANCELED`.

- `DRAFT` — редактируется локально.
- `READY` — прошёл проверку и утверждён пользователем.
- `QUEUED_LOCAL` — локально сохранён, **ещё не подтверждён сервером**; при выключенном ПК отправка не гарантирована.
- `QUEUED_SERVER` — сервер принял полный неизменяемый снапшот содержимого и все вложения.
- `SENDING` — начата попытка выполнения для одной цели.
- `SENT` — Telegram вернул подтверждённый успех с идентификаторами сообщений.
- `RETRY_WAIT` — временная ошибка, время следующей попытки.
- `FAILED` — ошибка, которую нельзя исправить повтором, либо исчерпано число попыток.
- `UNKNOWN_RESULT` — отправка могла состояться, но ответ потерян; **автоматически повторно не отправлять** до разбирательства.

### 8.2. Основные функции

- Назначение даты и времени для одного/нескольких каналов; **отдельное расписание каждого канала**.
- Календарь день/неделя/месяц, список очереди, сортировка, фильтры каналов, пауза/снятие паузы всей очереди и отдельных заданий.
- Перетаскивание карточек в календаре с подтверждением новой даты, переупорядочивание, пакетный сдвиг.
- Повторяющиеся публикации по правилам; каждая будущая отправка — самостоятельная запись и новый утверждённый снапшот. В v1.0 допускается повтор уже утверждённого контента, без автономной генерации нейросетью.
- Распределение N постов в выбранный интервал с шагом или по выбранным слотам; исключения дней недели/часов по каналу.
- Время хранить как UTC, рядом IANA time zone/локальное представление; в UI корректно объяснять неоднозначные/отсутствующие часы перехода DST.
- Сервер валидирует время и контент независимо от локального клиента. Изменение поста **после** постановки в очередь не меняет снимок на сервере молча; нужно действие «Обновить запланированную публикацию», новая ревизия и повторное подтверждение.
- Редактирование/отмена принимаются только пока публикация не захвачена на отправку; если уже `SENDING`, показать невозможность гарантировать отмену.
- Уведомления об успехе/ошибке доступны в интерфейсе при следующей синхронизации, а по желанию — в отдельном служебном Telegram-чате.

### 8.3. Правила доставки и повторы

- Один серверный worker, атомарное получение задания с lease и ограничением параллелизма. При падении процесса запись не должна оставаться навсегда `SENDING`.
- Для `429` использовать возвращённое Telegram `retry_after`; для `5xx` — ограниченный backoff с jitter; учитывать ограничения на чат/бота и временную потерю прав.
- `401/403`, неверный chat ID, отсутствующий медиафайл, неподдерживаемый формат — фиксировать `FAILED` с понятной ошибкой, не делать бесполезный бесконечный retry.
- Уникальные ограничения БД на целевые публикации, серверный `idempotency_key` для запроса постановки в очередь; **повтор того же REST-запроса не создаёт второе задание**.
- Telegram Bot API **не обеспечивает универсальную идемпотентность `sendMessage`**: если отправка ушла, но ответ потерян, нельзя честно обещать абсолютное отсутствие дублей. Такая цель переходит в `UNKNOWN_RESULT`, оператор получает инструкцию проверки и явное решение «Считать отправленным / Повторить вручную / Отменить».
- Для медиа-альбомов отдельно учитывать частично известные результаты и группы message IDs; не запускать повтор всей группы без проверки.
- Нельзя обещать «опубликовано точно в секунду»: целевой SLA на собственную обработку — запуск задания в течение 30 секунд от `scheduled_at` при работоспособном VPS и доступности Telegram; задержка Telegram и ограничения API не контролируются.

## 9. Серверная часть — только для always-on публикаций

### 9.1. Назначение и минимальная схема

```text
AiteBar / TelegramPostEditor (Windows)
  ├─ черновики, медиа, инструкции, генерация ИИ
  ├─ локальная SQLite и защищённые Telegram-токены
  └─ HTTPS → TelegramPostEditor.Server (Linux)
                 ├─ Minimal API: pairing, queue, status, media
                 ├─ SQLite (WAL): jobs, targets, attempts, channel config
                 ├─ media directory (атомарная загрузка и проверка hash)
                 ├─ BackgroundService: due-job poll, leasing, retries
                 └─ Telegram Bot API
```

- **Не переносить ИИ-систему AiteBar на сервер.** Сервер публикует только сформированные и утверждённые материалы.
- Сервер — небольшой отдельный сервис в том же репозитории, **не самостоятельное Windows-приложение**.
- Один экземпляр на одном VPS (требование для упрощённой SQLite-очереди). Если в будущем потребуется несколько серверов, это отдельное решение и миграция, не скрытая часть v1.0.
- Файлы хранить на постоянном диске, не во временном контейнере. На старте сервер проверяет миграции, доступность БД, директории медиа и права файлов.

### 9.2. Авторизация и конфиденциальность

- Первичная привязка клиента к серверу: администратор создаёт одноразовый код ограниченного срока жизни **локальной CLI-командой на VPS** (публичный запрос не должен выпускать коды без авторизации), пользователь подтверждает привязку в AiteBar; далее короткоживущий access token + безопасный механизм перевыпуска либо управляемый токен устройства.
- HTTPS обязателен вне локальной сети. Разделить токен авторизации AiteBar↔сервер, токены Telegram-ботов и ИИ-ключи.
- Для серверной публикации необходимо **однократно передать Telegram-токен бота** по защищённому каналу: сервер никогда не может прочитать Windows Credential Manager напрямую. Пользователь подтверждает предоставление бота серверу и может его отозвать.
- На сервере Telegram-токены хранить шифрованными (AEAD, например AES-256-GCM); master key — отдельная переменная окружения или защищённый файл вне каталога БД, права доступа минимальные; маскировать секреты в UI, логах и исключениях.
- Никаких сторонних логирующих прокси с телом сообщений или секретами; не записывать Authorization/бот-токены в query strings и логи.
- Ограничить размер загружаемых материалов; проверить типы и хеш, отклонять path traversal, защитить от SSRF при необязательном импорте URL.
- Сервер принимает только связанные с устройством каналы/боты и проверяет права на операции.

### 9.3. REST API (контракт v1; уточнить сериализацию DTO при реализации)

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/v1/pair/start` | Одноразовая привязка клиента |
| `POST` | `/api/v1/pair/confirm` | Подтвердить и выдать авторизацию |
| `GET` | `/api/v1/health` | Health/readiness без секретов |
| `GET` | `/api/v1/channels` | Список подключённых каналов |
| `PUT` | `/api/v1/channels/{id}` | Добавить/изменить канал и бота |
| `POST` | `/api/v1/media` | Загрузка медиа и проверка хеша |
| `POST` | `/api/v1/publications` | Создать планируемые цели с `Idempotency-Key` |
| `GET` | `/api/v1/publications?status=&from=&to=` | Список и статусы |
| `GET` | `/api/v1/publications/{id}` | Результаты и история попыток |
| `PATCH` | `/api/v1/publications/{id}` | Изменить время/снапшот до отправки, `If-Match` |
| `POST` | `/api/v1/publications/{id}/pause` | Пауза |
| `POST` | `/api/v1/publications/{id}/resume` | Возобновить |

Пример запроса постановки в очередь (поля иллюстративны, контракт должен быть закреплён DTO и тестом):

```json
{
  "clientPostId": "74c2d8ef-1f2b-4aca-b21d-067d1443794b",
  "revision": 3,
  "targets": [
    {
      "targetId": "9e0dad47-51c5-4c83-ac3a-bbe2a93343c3",
      "channelId": "channel-1",
      "scheduledAtUtc": "2026-11-18T10:00:00Z",
      "content": {"format": "telegram-document-v1", "text": "Текст публикации", "entities": []},
      "mediaIds": [],
      "options": {"disableNotification": false}
    }
  ]
}
```

Успешный ответ означает **«задание принято сервером»**, не «опубликовано в Telegram». Возвращать `serverPublicationId`, сохранённый `revision`, статусы по всем target и ошибки валидации. Синхронизация по курсору событий плюс периодическое полное согласование при восстановлении.

## 11. Экспорт, резервирование, восстановление

- Экспорт постов и шаблонов в структурированный JSON (версия схемы), экспорт текста в TXT/Markdown там, где форматы допускают корректную передачу оформления.
- Экспорт библиотеки с вложениями в архив с manifest/sha256, защита от path traversal при импорте.
- **Встроиться в существующий механизм резервного копирования AiteBar**: утилита предоставляет набор файлов/данных и правила восстановления; не дублирует общий UI резервирования.
- Секреты ИИ не экспортировать отдельным механизмом утилиты. Telegram-токены — только через действующий безопасный режим резервирования приложения (если поддерживает произвольные секреты), иначе требовать повторного ввода после восстановления; не записывать их в обычный архив.
- Сервер: ежедневная согласованная копия SQLite и медиа, опция восстановления на новый VPS, документированная процедура ротации master key/перевыдачи Telegram-токенов.
- Контроль: восстановленная версия содержит все черновики, инструкции, медиа и актуальное локальное состояние очереди; не потерять события, полученные от сервера.

## 12. Журнал событий и диагностика

- Раздел «Журнал» (в рамках интерфейса утилиты) с фильтрами: дата, канал, пост, статус.
- События: создан, изменён, ИИ-вариант получен/применён, проверен, отправлен на сервер, принят сервером, отправка начата, успех, ошибка, неизвестный результат, редактирование/удаление в Telegram.
- Сетевые ошибки выводить пользователю понятно: «Бот удалён из канала», «Сервер недоступен», «Ограничение Telegram до ...», «Медиа отсутствует».
- Диагностическая выгрузка (без токенов, без тел сообщений по умолчанию) с correlation ID для клиентских и серверных операций.
- Учитывать существующие `Logger`/телеметрию AiteBar; не создавать отдельную систему сбора персональных данных.

## 13. Нефункциональные требования

- Поддержка Windows 10/11 в пределах текущих системных требований AiteBar; без дополнительного внешнего рантайма редактора.
- Открытие окна с локальной библиотекой из 1000 текстовых постов — ориентир ≤2 с на обычном SSD, исключая сетевую синхронизацию; плавное редактирование поста около 20 000 символов на целевом оборудовании.
- Список/календарь должны виртуализировать большие наборы элементов; тяжёлую загрузку превью медиа не выполнять в UI-потоке.
- Пользовательские данные **не теряются** при закрытии окна после успешного локального сохранения; при сбое запись восстанавливается из консистентной SQLite-транзакции и recovery-журнала.
- Асинхронные операции с `CancellationToken`; нельзя блокировать Dispatcher/WPF-поток сетевым запросом.
- Защита от дублирующего нажатия «Опубликовать», конкурентного изменения поста и конфликтных обновлений очереди.
- Секреты и токены не пишутся в логи, не попадают в обычные JSON-настройки или общий текстовый экспорт.
- Сервер автоматически поднимается после перезагрузки VPS, сохраняет очередь, а если сеть недоступна — повторяет только безопасные операции по правилам §8.3.
- Локализация и горячие клавиши — как принято в AiteBar; новая утилита не меняет поведение остальных инструментов.

## 14. Тестирование: обязательные сценарии приёмки

**Запуск и совместимость AiteBar**

AT-01. Новая кнопка отображается в общем каталоге, открывает ровно одно рабочее окно, скрывается/показывается стандартной настройкой; другие кнопки/горячие клавиши не сломаны.  
AT-02. Сохранённые панели, Quick Note, Zen Editor, Text Processing и PromptBuilder работают после установки обновления; сохранённые ИИ-провайдеры и ключи не мигрируют и не запрашиваются повторно.  
AT-03. Окно соответствует существующим ресурсам AiteBar, работает на нескольких масштабах DPI, корректно открывается на разных мониторах и не скрывается как оверлей при потере фокуса.  

**Редактор, медиа и предпросмотр**

AT-04. Черновик с несколькими абзацами, ссылками, жирным, курсивом, спойлером и медиа корректно сохраняется, закрывается, открывается без потери форматирования; Undo/Redo работает.  
AT-05. Автосохранение и аварийное восстановление проходят без потери ранее зафиксированной ревизии.  
AT-06. Превью меняется при правке, валидатор блокирует неподдерживаемые для выбранного метода сущности и неподходящее медиа; конечный тестовый пост визуально соответствует поддерживаемым Telegram-элементам.  
AT-07. Тестовая публикация отправляется только в тестовый канал; никакая основная цель не меняет статус.  

**ИИ и инструкции**

AT-08. Модель и ИИ-подключение выбираются из существующих настроек AiteBar; для генерации **не требуется добавлять ключи ещё раз**.  
AT-09. Генерация/редактирование выдаёт отдельный результат; «Отклонить» оставляет черновик неизменным, «Применить» создаёт новую ревизию.  
AT-10. Можно создать три разные инструкции, переключать их, назначить инструкцию по умолчанию каналу; версия, использованная для генерации, сохраняется.  
AT-11. При ошибках ИИ утилита показывает ответ общего шлюза; не вводит собственного механизма ротации и не изменяет параметры существующих подключений.  

**Telegram и несколько каналов**

AT-12. Один пост отправлен в два канала, получены два независимых успеха, Telegram IDs и корректные ссылки там, где Telegram позволяет их сформировать.  
AT-13. Для третьего канала получена ошибка прав: другие каналы остаются в успехе, повторная попытка не дублирует успешные публикации.  
AT-14. Редактирование и удаление опубликованного текстового поста работает в границах Telegram; запрещённый тип редактирования даёт понятное сообщение без потери исходной записи.  
AT-15. Повторная публикация создаёт новый target, а не перезаписывает историю старого.  

**Очередь и сервер**

AT-16. Десять постов на неделю поставлены в очередь; сервер подтвердил каждый снапшот и каждое медиа, пользователь закрыл AiteBar и выключил Windows; публикации происходят по расписанию с учётом доступности VPS/Telegram.  
AT-17. Если сервер недоступен при постановке в очередь, интерфейс **не показывает** `QUEUED_SERVER`; локальные черновики остаются сохранёнными.  
AT-18. Одновременные/повторные запросы с одним `Idempotency-Key` не создают второй target; смена даты до отправки создаёт новую серверную ревизию.  
AT-19. Сервер перезапущен при наличии заданий; очередь восстановилась, безопасные незавершённые операции обработаны по правилам lease и retry.  
AT-20. Telegram возвращает 429 с `retry_after`: повторная попытка выполняется не раньше указанного времени.  
AT-21. Соединение оборвано после отправки тела Telegram-запроса и до получения ответа: `UNKNOWN_RESULT`; **автоматического дублирования нет**.  
AT-22. Пауза, восстановление, отмена, изменение даты и времени действуют до начала отправки, а невозможность отменить `SENDING` показана явно.  
AT-23. Два канала одной публикации имеют разные тексты и разное время; отправлен правильный вариант в нужный канал.  

**Безопасность, сохранность, сборка**

AT-24. Ни клиентские логи, ни серверные логи, ни экспорт черновиков не содержат API-ключей ИИ, Telegram-токенов и токенов авторизации.  
AT-25. Резервное копирование/восстановление переносит посты, вложения, инструкции, метаданные очереди без повреждения исходных данных; секреты не экспортируются в незашифрованном виде.  
AT-26. Без сервера редактор сохраняет локальные черновики и позволяет прямую отправку «сейчас», но **не обещает** отправку при выключенном ПК.  
AT-27. `dotnet build AiteBar.sln -c Release`, `dotnet test AiteBar.Tests/AiteBar.Tests.csproj -c Release`, серверные тесты и сборка действующего инсталлятора завершаются успешно.  
AT-28. Удаление/отключение утилиты из панели не удаляет её данные и не меняет настройки других утилит.  
AT-29. Сравнение двух существующих ИИ-моделей запускает только подтверждённые запросы, результаты независимы, применение одного не разрушает исходный черновик.  
AT-30. Экспорт/импорт корректного документа сохраняет оформление и историю; неподдерживаемые элементы явно отмечаются, ни один секрет не попадает в файл.

Критерий приёмки релиза: **все AT-01...AT-30 успешны**, нет заглушек в обязательных сценариях, серверная публикация проверена на реальном тестовом канале; исключения и ограничения задокументированы.

## 15. Порядок реализации

**Этап 0 — сверка актуального репозитория (обязателен).** Проверить `AiteBar.csproj`, `UtilityRegistry`, `UtilityButtonCatalog`, `ActionService`, `AppSettingsService`, `AiGateway`, `DarkWindow`, `QuickNote`, `ZenEditor`, `TextProcessing`, тесты и систему backup. Зафиксировать различия между текущим кодом и копией из Google Drive. Не изменять дизайн и ИИ-провайдеров.

**Этап 1 — каркас утилиты.** Регистрация, окно `Workspace`, локализация, стандартные настройки видимости, горячая клавиша по паттернам проекта, тесты интеграции с AiteBar.

**Этап 2 — хранилище и редактор.** SQLite, миграции, PostDocument, автосохранение, папки/поиск/теги, форматирование, медиа, шаблоны, восстановление, тесты сериализации.

**Этап 3 — ИИ-инструкции и интеграция.** Локальная библиотека инструкций; выбор существующей модели через `AiGateway`; потоковое предложение, дифф и применение, метаданные ревизий. Никаких новых провайдеров.

**Этап 4 — Telegram.** Боты, каналы, локальное защищённое хранение Telegram-токенов, превью, валидация, отправка «сейчас», тестовая публикация, мультипубликация, история, редактирование, удаление и кнопки.

**Этап 5 — серверный планировщик.** ASP.NET Core, SQLite, пары device/server, передача разрешённых bot secrets, медиа, API и worker; очередь, календарь, пауза, повторение безопасных ошибок, `UNKNOWN_RESULT`.

**Этап 6 — выпуск и регрессия.** Backup/restore, нагрузочные и end-to-end тесты, документация, журнал ошибок, стандартная сборка и инсталлятор AiteBar.

Для каждого этапа: код, тесты, успешная сборка, сценарий ручной проверки и краткий отчёт об изменённых файлах. Следующий этап не «прячет» ошибки предыдущего.

## 16. Состав поставки и критерии завершённости

1. Изменения **в действующем репозитории AiteBar** с новой рабочей утилитой и минимальными интеграционными изменениями.
2. Сервер `TelegramPostEditor.Server` с конфигурационным примером **без реальных секретов**, schema migration, systemd unit (или Compose при реальной необходимости), скриптами резервирования/восстановления.
3. Unit/integration/e2e-тесты и журнал результатов AT-01...AT-30.
4. Пользовательская документация: подключить бота, выдать права каналу, подготовить пост, выбрать ИИ-инструкцию, сделать тестовую отправку, запланировать публикации, проверить статусы, восстановить сервер.
5. Инструкция развёртывания на имеющемся Linux VPS/Oracle Cloud с HTTPS, медиа и постоянным хранилищем, без зависимости от Windows для публикации.
6. Одна релизная поставка **AiteBar** через существующий инсталлятор и существующий процесс версионирования; никакого отдельного клиента Telegram Post Editor.
7. Описание ограничений API, корректного поведения при неопределённом результате и различий между серверной и локальной доставкой.

**Определение готовности:** не прототип интерфейса и не частично работающая отправка; все согласованные обязательные функции доступны через AiteBar, ключи ИИ не дублируются, существующие утилиты не сломаны, сервер действительно публикует при выключенном клиентском ПК и результаты подтверждены тестами.

## 17. Перспективные функции — за пределами релиза 1.0

Ниже сохранены обсуждавшиеся возможности, но **они не блокируют приёмку релиза 1.0 и не разрешают переработку провайдеров или дизайна**:

1. RSS-ленты и автоматизированный импорт статей в **черновики** со ссылкой на источник и ручным подтверждением; публикация без человека не допускается по умолчанию.
2. Входящий рабочий Telegram-бот для пересылки материалов в редактор в пределах доступных Bot API событий и прав.
3. Расширенная аналитика постов: только метрики, доступные через выбранные официальные API или по согласованным внешним интеграциям; не обещать произвольную историю просмотров/реакций.
4. Роли автор/редактор/администратор, согласование, совместная работа, журнал утверждений.
5. Автогенерация контент-плана и предложений времени с сохранением обязательной финальной проверки.
6. Отдельные мобильный и веб-клиенты — **только как будущая самостоятельная задача**; текущая реализация остаётся WPF-утилитой AiteBar.
